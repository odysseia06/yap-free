# Shared decision rules

Every expression, element, or step should help its intended audience identify something, act, understand a relevant state, decide, learn, or recover. Judge task clarity and preserved function, not word count. Keep effective content unchanged; necessary explanation may need to be added.

This is the single source of common rules for all yap-free entries. Domain guidance adds context without weakening these protections. Read the core once per task, including from a direct domain entry; do not invoke the root router from a domain.

## Establish the task and authority

Identify the target artifact, purpose, audience, existing context and terminology, verified behavior, requested mode, and allowed scope. Familiarity depends on the audience: beginner instruction and expert reference have different needs. Respect the user's brief, requested voice, existing conventions, and current edits.

Use the request and available source or implementation to resolve uncertainty. Ask only for missing facts that materially affect correctness or risk losing an important function. Do not make the user fill in a decision template or repeat authorization for clear, reversible edits already in scope. Higher-priority host instructions and tool permissions always apply; this skill grants no additional access or authority.

## Decide before writing

Reason internally about each candidate: What useful role does it serve? Is the same information already available in this context? Would removing it lose required meaning or function? Are its claims verified? Do not invent a confused user to justify extra copy. Prefer a clearer label, familiar control, or grouping when it resolves a real ambiguity within scope, without redesigning unrelated content or layout.

| Decision | Evidence required |
| --- | --- |
| Delete | No useful role, or unnecessary repetition of the same function in the same context; required information and function remain available. A shorter useless sentence is still useless. |
| Rewrite | Necessary information is unclear, misplaced, or indirect; retain its meaning, conditions, consequences, and voice. |
| Keep | Already effective, or removal would lose knowledge, control, accessibility, learning, recovery, or requested expression. Repetition in separate contexts can be necessary. |
| Add | A task-relevant fact, state, condition, or recovery explanation is missing and supported by verified behavior. Place it where it affects the action or decision. |
| Investigate or ask | Available context does not resolve a material risk of losing an important function. Investigate first; continue independent, clearly scoped work while the unresolved part waits. |

An evidently redundant tooltip with no other function can be removed during an authorized fix, including obsolete references to it. A confirmation explaining irreversible loss has a distinct function and must survive. Do not apply banned-word lists, sentence quotas, or automatic shortening rules in place of these decisions.

## Preserve what the audience needs

- Accurate meaning, facts, scope conditions, units, prerequisites, required sequence, limitations, relevant consequences, and required disclosures.
- Meaningful labels and accessible names, input requirements, legends, and keyboard or screen-reader access. Essential guidance must remain available without hover; placeholders and unexplained icons cannot replace required labels.
- Honest loading, progress, saving, success, and failure states; usable control, actionable errors, and verified recovery. Do not invent guarantees, limits, behavior, or recovery options.
- Safety and permission boundaries, important confirmations, and established machine or behavior contracts. Concision is no reason to remove these functions.
- Context-appropriate voice and explicitly requested marketing, educational, editorial, or narrative purpose. Length alone does not make a lesson or story redundant.

Keep unknown, unmeasured, absent, and false distinct; simplifying a claim must not turn lack of evidence into evidence of absence. Required conditions and disclosures belong in the artifact its audience receives. Mentioning them only in the completion message does not preserve them in that artifact.

Do not add text to fill space or descriptions under every item by default. Keep implementation notes out of audience workflows unless they help that audience perform the task.

## Apply the requested mode

**Generate:** Build the requested artifact around necessary information and actions. Explanations, introductions, and closing summaries each need a useful role; their absence is not a goal either. Check relevant states, audience needs, conditions, and recovery.

**Audit:** Evaluate without changing artifacts, even when tools allow writes. Ground findings in real locations, user impact, a suitable decision, and the functions that must survive. If no supported issue exists, say so without manufacturing findings. Scale the report to the request; do not add audit panels or rule explanations to the product.

**Fix:** Apply authorized changes within scope, including functionless elements or steps where their removal is supported. Preserve existing user edits. Do not change unrelated layout, business rules, permission checks, important confirmations, or behavior contracts merely to simplify. If a tool denies a change, report the proposed change and exact blocker; do not claim it was applied.

## Verify and report

Review the completed result for repeated meaning, remaining ambiguity, protected functions, and factual support. Match verification to the change: meaning and conditions for text; labels, focus and state flow for UI removal; output contracts for CLI; steps and sources for docs; claims, sources, uncertainty and actual completion for AI messages. State when runtime or other relevant verification was unavailable.

Report meaningful changes or findings, actual verification, and unresolved uncertainty. Keep internal reasoning and routine decision logs out of the artifact and response; include the rationale the user needs to assess a material decision. Never describe an unrun check, denied action, or proposed edit as completed.
